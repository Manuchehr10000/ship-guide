# Ship — руководство

*Это публичная копия руководства. Она публикуется из закрытого репозитория набора при каждом релизе, поэтому правки здесь перезаписываются.*

**v0.1.6 — 6 ноября 2026.** Перевод английской версии v0.1.6 для ship-spec 0.6.0 и плагина mg-ship-kit 0.6.0. Части про деплой (конец шага 5, шаг 8 и главы по трекам) остаются краткими до первых прогонов на каждом треке и будут переписаны по их итогам. Где руководство и набор расходятся, прав набор. Главный текст — английский, [README.md](README.md); при расхождении верен он. Это руководство описывает набор (kit) и никогда не копирует его файлы: точные колонки и команды — по ссылкам.

Вы здесь впервые? Откройте новый чат Claude, вставьте ссылку на эту страницу и попросите провести вас по шагам 1–6.

## Что такое Ship

Создавать, выпускать и поддерживать софт, за который платят, без команды разработчиков.

Вы описываете один небольшой кусок (piece) в чате Claude. Он попадает в трекер проекта в Notion со статусом Ready. Claude Code берёт его, собирает и не может отправить на dev, пока кусок не совпадёт с контрактом, не будет использовать только согласованный стек и не избавится от неиспользуемого кода. Клиент проверяет его на dev; его решение закрывает кусок. Релиз в main ждёт, пока ничего не собирается и у каждого куска на dev есть решение.

Правила, на которых всё держится:

- Вы утверждаете один короткий экран на кусок — контракт. Подробный план Claude нужен Claude, а не вам.
- Собирайте малое на dev и давайте клиенту проверять там. То, чем никто не пользуется, удаляется, а не прячется. Git всё помнит.
- Проваленная проверка останавливает кусок. Сначала чините проверку. Без исключений.
- Каждое решение приходит к вам как одна реальная ситуация, два-три варианта, цена каждого простыми словами и рекомендация. Не поняли — берите рекомендацию.
- Ничто не фиксируется, пока вы не скажете «да» своими словами. Молчание, вопрос или «если не возражаете» не считаются.
- Любая смена курса помечается одной строкой: «CHANGE: …».
- Правила Ship живут в наборе, а не в вашем проекте: чат берёт их из скилла ship-spec, Claude Code — из плагина. Собственные файлы проекта хранят только то, что верно для этого проекта, поэтому изменение набора доходит до каждого проекта без ручного копирования.

## 1. Настройка один раз

На каждого человека и каждую машину. Делается один раз; пункт 8 говорит, что повторять после изменения набора.

1. **Claude.** Установите приложение Claude для компьютера и войдите с планом, в который входит Claude Code. Вкладка Code — ваша мастерская. Терминал и VS Code — продвинутые пути; они вам не нужны.
2. **GitHub.** Аккаунт. Репозиторий набора закрытый: попросите владельца добавить вас в организацию mgac-consulting (хватит роли Read). Чтобы Ship работал в облачных сессиях, владелец организации также ставит GitHub-приложение Claude на mgac-consulting с доступом к ship-kit: один раз на организацию, не на каждого.
3. **Notion.** Рабочее пространство, где вы можете добавлять тимспейсы. В аккаунте Claude включите коннектор Notion; вкладка Code пользуется им, когда вы входите с тем же аккаунтом.
4. **На машине.** git и python3; Node.js, если у проектов есть фронтенд. Доступ к GitHub из вкладки Code: `gh auth login`, затем `gh auth setup-git`, или SSH-ключ. Попросите Claude во вкладке Code провести вас по шагам.
5. **Скилл для чата.** Возьмите zip `ship-spec` у владельца набора или сами заархивируйте папку [`chat/ship-spec`](https://github.com/mgac-consulting/ship-kit/blob/main/chat/ship-spec) из набора (оба файла). Загрузите его как скилл в свой аккаунт Claude. Строка Version в нём говорит чату, какая версия установлена. Повторяйте после каждого изменения набора.
6. **Плагин.** Во вкладке Code выполните `/plugin marketplace add mgac-consulting/ship-kit`, затем `/plugin install mg-ship-kit@ship-kit`. Вкладка Code в приложении ставит плагины так же, через меню `+`. Эта установка — только для вашего компьютера: облачные сессии её не видят. Они загружают плагин из репозитория проекта, после того как там выполнен `/mg-ship-kit:setup` (шаг 5).
7. **Проверка.** В новом чате вопрос «что умеет ship-spec?» получает ответ. Во вкладке Code команда `/mg-ship-kit:setup` есть в списке команд.
8. **После изменения набора.** README набора говорит, что изменилось. Большая часть теперь приходит сама:
   - **Плагин** обновляется сам в фоне, через несколько минут после начала сессии (настройка включает это на шаге 5). Чтобы получить сразу: `/plugin marketplace update ship-kit`, затем в `/plugin` откройте Installed → mg-ship-kit → Update now, затем `/reload-plugins`.
   - **Каждый проект** — на следующей сессии Claude Code в нём: плагин открывает PR в репозитории, который обновляет проверку GitHub, а Claude обновляет строку Kit на странице проекта. Слейте PR в dev, затем подтяните dev. Для PR нужен `gh` с входом; без него Claude скажет выполнить `/mg-ship-kit:setup` и закоммитить `.github/`.
   - **Страница проекта** получает новую колонку или строку от самого чата перед его следующей задачей. Он только добавляет.
   - **Скилл чата** — единственное, что вы делаете вручную: изменилась папка `chat/` — повторите пункт 5. Помнить не нужно: перед каждой задачей чат сравнивает свою версию со строкой Kit проекта и останавливается с «Re-upload ship-spec», если отстал.

   **Один раз, для 0.6.0:** в каждом проекте откройте сессию Claude Code и один раз выполните `/mg-ship-kit:setup`. Он включает автообновление, убирает из `CLAUDE.md` старые строки правил набора (они теперь приходят из плагина) и просит строку Kit. Затем в чате скажите «give me the project instructions» и вставьте их в Claude Project проекта (шаг 4, пункт 5). **Один раз, для 0.4.0:** плагин переименован из `ship` в `mg-ship-kit`, поэтому обновление его не переносит. Выполните `/plugin uninstall ship@ship-kit`, затем `/plugin install mg-ship-kit@ship-kit`, затем `/reload-plugins`. В каждом проекте выполните `/mg-ship-kit:setup` и замените в его `CLAUDE.md` любую команду `/ship:` на `/mg-ship-kit:`; до этого setup будет предупреждать.

## 2. Notion: тимспейс проекта

1. В боковой панели Notion добавьте тимспейс с именем проекта (например «Acme CRM»). Один тимспейс на проект.
2. Участники: вы и ваша команда. Никогда не добавляйте клиента и никогда не делитесь страницей оттуда. Клиент видит продукт на dev и в проде, но не этот тимспейс.
3. Не создавайте в нём страниц вручную. Страница проекта появится на шаге 4.

## 3. GitHub: репозиторий проекта

1. Создайте закрытый репозиторий с именем проекта и README, чтобы в нём был первый коммит. Или во вкладке Code: «создай закрытый репозиторий GitHub с именем … и ветками main и dev и склонируй его сюда».
2. Две ветки. `main` — то, что работает в проде. `dev` — куда попадают куски и где проверяет клиент. Создайте `dev` из `main`.
3. Склонируйте репозиторий на машину и откройте его папку во вкладке Code.
4. Секреты (пароли, ключи, доступы к серверу) живут в env-файле, например `.env`, который git игнорирует. Добавьте `.env` в `.gitignore` до любого коммита, в который он мог бы попасть; первый коммит с одним README — не страшно. Позже настройка добавит все строки для env-файлов, и с того момента push с env-файлом не пройдёт; но файл, закоммиченный раньше, останется в истории git.
5. Существующий проект остаётся в своём репозитории. Пропустите пункт 1, но сделайте пункты 2–4: две ветки, клон, строка про env. Список стека читается из его файлов зависимостей.

## 4. Чат: страница проекта

1. В новом чате Claude скажите «start a project». Отвечает скилл ship-spec.
2. Он перечисляет ваши тимспейсы и спрашивает недостающее: имя проекта, одну строку о том, что он делает, как продаётся (один клиент, несколько клиентов или публичное приложение), каждого клиента с контактом, ссылку на репозиторий и где хранятся секреты. По строке на каждое. Для остального годится «not yet».
3. Он выбирает трек (track): где проект работает и на каком стеке. Он задаёт до четырёх простых вопросов (есть ли клиент — банк, телеком или госорган? есть ли в команде devops? в основном работа с данными или страницы и формы? можете ли платить картой от $5 в месяц?) и называет трек с причиной: devops, railway или cloudflare. Вас никогда не спрашивают «какой стек?». Если хотите другой трек и можете сказать почему, скажите: ваш трек и ваша причина попадут в строку Track. Если клиент — банк, телеком или госорган, а devops нет, всё останавливается здесь: сначала найдите devops.
4. Он строит страницу в корне тимспейса, читает её обратно и проверяет, что все части на месте. Вы получаете ссылку.
5. Он даёт короткий блок инструкций для Claude Project этого проекта. Создайте Claude Project с именем проекта и вставьте блок в его инструкции, один раз. Менять его не нужно: он велит чату загружать ship-spec и хранит только стиль ответов (один экран, одно решение, ничего не фиксируется без вашего «да»). Всё остальное приходит из скилла, который обновляется вместе с набором. Потеряли — скажите «give me the project instructions».
6. Последней строкой он отправляет вас к `/mg-ship-kit:setup`. Пока ничего не описывайте: сначала настройте репозиторий (шаг 5) и пройдите чек-лист (шаг 6).

Страница сверху вниз. Точные строки, колонки и представления лежат в [chat/ship-spec/page-layout.md](https://github.com/mgac-consulting/ship-kit/blob/main/chat/ship-spec/page-layout.md); руководство их не копирует.

| Часть | Что в ней | Кто пишет |
| --- | --- | --- |
| Facts (факты) | Постоянные факты и ссылки: что делает, как продаётся, трек, клиенты и контакты, репозиторий, ссылки на dev и прод, папка на Drive, дизайн-система, где хранятся секреты. Сами секреты — никогда. | Чат при старте; вы поправляете |
| Tracker (трекер) | Одна строка на кусок: имя, порядок, статус (Ready → Building → On dev → Done, или Dropped), размер, файл контракта. Полный контракт лежит внутри строки. | Чат добавляет строки Ready; после взятия в работу — только Claude Code |
| Meetings (встречи) | Одна строка на встречу с клиентом, заметки в теле. Отмечается галочкой, когда каждый запрос разнесён. | Вы; галочку ставит чат |
| Backlog (бэклог) | Одна строка на запрос: кто сказал (клиент, ваши заметки о клиенте, пользователь, ваша идея, конкурент), точные слова, какой клиент просил, статус (New → Specced, или Dropped), ссылка на кусок и его живой статус. | Чат, из того, что вы ему даёте: заметки встречи, идея, скриншот, слова пользователя. Строку можно добавить и руками |
| Notes (заметки) | Ваши. Ни один инструмент их не читает. | Вы |

Правила для всей страницы: нигде ни пароля, ни ключа, ни доступа к серверу. Представления сортируют и никогда не фильтруют. Строки помечаются Dropped, а не удаляются.

## 5. Code: настройка репозитория

1. На своём компьютере, во вкладке Code, в папке репозитория, выполните `/mg-ship-kit:setup`. Первую настройку нельзя сделать в облачной сессии: плагина там ещё нет. Сначала он просит ссылку на страницу проекта. Вставьте её. Он читает трек из Facts. На треке cloudflare он останавливается здесь и ничего не пишет: этот трек ещё не построен.
2. Он находит папки бэкенда и фронтенда и пишет `ship.json` со списком стека, прочитанным из файлов зависимостей. В пустом репозитории он берёт стек набора по умолчанию (FastAPI, Postgres, React, в `backend/` и `frontend/`) — это стек треков devops и railway. Если в строке Track назван другой стек, скажите сейчас; тогда он начнёт с пустого списка и нужных папок.
3. Он читает список стека обратно: «n Python packages, n Node packages». С этого момента всё новое останавливает кусок, пока вы не одобрите одной строкой.
4. Он создаёт `contracts/` и `CLAUDE.md` из шаблона набора. Заполните заготовки вместе с Claude по тому, что видно в коде. `CLAUDE.md` хранит только то, что верно для этого проекта: что это, его стек, его команды, его собственные правила. До 150 строк, без кода. Правил Ship в нём нет: плагин добавляет их в каждую сессию, поэтому они обновляются вместе с плагином. В уже существующем `CLAUDE.md` настройка убирает строки, копирующие старые правила набора, и добавляет одну строку о том, откуда берутся правила. Строка набора, которую вы правили вручную, остаётся; Claude показывает её и спрашивает: удалить или оставить как правило проекта.
5. Он привязывает трекер на странице, которую вы вставили, и говорит «linked the tracker». Затем пишет строку Kit в Facts (`Kit: mg-ship-kit` и версия). Чат проверяет эту строку перед каждой задачей, так что устаревший скилл чата или устаревший плагин видны сразу.
6. Он называет каждый инструмент проверки — `vulture` для бэкенда и `knip` для фронтенда — как найденный, как MISSING со строкой установки или как «needed once backend/ exists» в пустом репозитории. MISSING ставьте сейчас; «needed once» — как только первый кусок создаст эту папку, до `/mg-ship-kit:cto-check`. Без них проверка не проходит. Если он предупреждает, что git отслеживает env-файл, уберите файл из git, как он говорит, и смените любой пароль, который там был.
7. Он записывает проверку GitHub в `.github/`. С этого момента GitHub прогоняет ту же проверку при каждом push в dev и main, и ничего не деплоится, пока она не пройдёт. Не правьте эти файлы. После обновления плагина он сам открывает PR, который их обновляет, на следующей сессии; слейте его. Ещё он добавляет env-файлы в `.gitignore`, и с этого момента любой push с таким файлом не пройдёт.
8. Он записывает плагин в `.claude/settings.json` и не трогает остальное в этом файле. Когда файл попадёт в dev, облачная сессия в этом репозитории получит команды Ship без установки — если GitHub-приложение Claude имеет доступ к репозиторию набора (шаг 1, пункт 2). Ещё он включает автообновление — там и в ваших собственных настройках Claude Code, — так что новый плагин приходит сам.
9. Закоммитьте добавленные и изменённые файлы и отправьте их в dev. В этом push нет кода продукта, поэтому шлюз его пропускает. Затем откройте на GitHub вкладку Actions репозитория: через несколько минут проверка Ship check для этого push становится зелёной. Красная или её нет: остановитесь и почините. Каждый деплой ждёт её. Тесты набора подменяют GitHub, так что первый push вашего проекта — настоящая проверка workflow; если она красная, сначала прочитайте лог запуска.
10. Подключите деплой. Настройка заканчивается одной строкой для вашего трека; подробности — в `.github/ship/README.md` в вашем репозитории. Трек devops: отдайте этот файл своему devops (раздел «Your devops»); его деплой запускается только после того, как прошла Ship check. Трек railway: следуйте разделу «Railway» и попросите Claude провести вас по шагам.
11. Когда ссылка на dev открывается, запишите её в строку Dev URL в Facts. Ждать её не нужно: описывайте и собирайте, пока деплой настраивается. Кусок, который попал на dev раньше, ждёт там ссылку и решение клиента. Live URL появится с первым релизом (шаг 8).

## 6. Чек-лист настройки: ничего не описывается и не собирается, пока не отмечен каждый пункт

Пока отмечается вручную; команды для этого в наборе ещё нет. В файле на GitHub галочки не ставятся, поэтому читайте его как список или скопируйте в Notes проекта.

**Notion**

- [ ] У проекта свой тимспейс, и в нём только вы и ваша команда.
- [ ] Страница проекта лежит в корне тимспейса и показывает все пять частей: Facts, Tracker, Meetings, Backlog, Notes.
- [ ] В Facts указано, что проект делает, как продаётся, трек, каждый клиент с контактом, репозиторий и где хранятся секреты.
- [ ] Нигде на странице нет пароля, ключа или доступа к серверу.

**Репозиторий**

- [ ] Закрытый репозиторий с `main` и `dev`, и вы можете отправлять в обе ветки из вкладки Code.
- [ ] Env-файл есть в `.gitignore` и никогда не коммитился.
- [ ] `ship.json`, `contracts/`, `CLAUDE.md`, `.gitignore`, `.claude/settings.json` и `.github/` закоммичены и отправлены в dev.
- [ ] Во вкладке Actions на GitHub проверка Ship check для этого push зелёная.
- [ ] `CLAUDE.md` заполнен, до 150 строк, и хранит только факты этого проекта; его первые строки говорят, что правила Ship приходят из плагина.
- [ ] Список стека прочитан вам обратно и совпадает с тем, что вы собираетесь использовать.
- [ ] Трекер привязан: шаг привязки сказал «linked the tracker», или повторный запуск настройки говорит «tracker:» со ссылкой.
- [ ] В Facts есть строка Kit с версией плагина.
- [ ] Настройка не назвала ни одного инструмента MISSING. Инструмент «needed once backend/ exists» пока не страшен: вы ставите его вместе с первым куском.

**Claude**

- [ ] ship-spec установлен и сделан для этого набора: чат сверяет его со строкой Kit перед каждой задачей.
- [ ] У проекта есть свой Claude Project, и в его инструкции вставлен блок из чата.
- [ ] Плагин mg-ship-kit установлен во вкладке Code, и `/mg-ship-kit:next` есть в списке команд.
- [ ] Облачная сессия на ветке dev репозитория тоже показывает `/mg-ship-kit:next`.
- [ ] Коннектор Notion включён, и вкладка Code открывает страницу проекта.

## 7. Сборка куска

**Сбор запросов (чат)**

- После встречи с клиентом добавьте строку в Meetings с заметками в теле: набранными, вставленными или текстом записи. Затем скажите «file the meeting». Чат перечисляет каждый запрос, слова скопированы точно; вы говорите «да»; каждый становится строкой Backlog.
- Ваша идея или экран конкурента: «add an idea», со скриншотом. Отзыв, тикет или сообщение пользователя: вставьте его; оно разносится как слова пользователя и никогда не переформулируется.
- Ничего не выдумывается. Запрос, которого нет в Backlog, сначала добавляется.

**Описание (чат)**

- Скажите «spec a piece». Чат показывает запросы New; вы выбираете один или несколько. Он набрасывает контракт на один экран: слова, из которых он вырос; что видят пользователи; чего нет; как проверить («When I …, then I see …»); размер в числах — экраны, эндпоинты, таблицы.
- Прочитайте. Утвердите одной строкой или скажите, что поменять. После утверждения кусок получает строку Tracker со статусом Ready, а его запросы становятся Specced и ссылаются на него.
- Если одна проверка клиентом его не покрывает, разделите на куски — или опишите как цепочку (ниже), чтобы Claude Code собрал части за один прогон. Куски собираются по одному.

**Взятие в работу и сборка (вкладка Code)**

- Выполните `/mg-ship-kit:next`. Он берёт кусок Ready с наименьшим Order, сохраняет контракт в `contracts/`, ставит строке Building и записывает в неё копию только для чтения. Эту копию пишет только Claude Code; правка вручную его останавливает.
- Claude собирает то, что перечислено в контракте, и ничего больше. Вы читаете один экран, а не план.
- Изменение, которое клиент просит по ходу сборки, — это изменение контракта: вы одобряете его одной строкой. Claude никогда не правит контракт сам.

**Проверка (вкладка Code)**

- Выполните `/mg-ship-kit:cto-check`. Три проверки: Size (что собрано против списка), Stack (пакет или импорт вне списка), Leftovers (неиспользуемый код в добавленных строках, его находят vulture и knip). Проваленная проверка останавливает кусок.
- Выход. Лишнее, о чём просил клиент: вы одобряете изменение контракта одной строкой. Лишнее, о чём никто не просил: Claude удаляет. Новый пакет: вы одобряете одной строкой, или Claude убирает его. Leftovers: Claude удаляет. Затем проверка идёт снова.
- При прохождении Claude может предложить строку-две для `CLAUDE.md` из того, чему научил кусок. Одобрите одной строкой или откажите.

**На dev (вкладка Code)**

- Скажите «push». Шлюз (gate) прогоняет проверку ещё раз и не пропускает незакоммиченные изменения; GitHub прогоняет её ещё раз, прежде чем что-либо деплоится. Строка переходит в On dev.
- Попросите клиента проверить кусок на Dev URL по строкам «How to check it».
- Сразу начинайте следующий кусок через `/mg-ship-kit:next`. Куски на dev не блокируют следующий.

**Решение клиента (вкладка Code)**

- Принято: `/mg-ship-kit:done`. Строка становится Done.
- Отклонено: `/mg-ship-kit:drop`. Код удаляется, строка становится Dropped. Git всё помнит.
- Почти верно: пока — оставьте на dev, занесите правку как новый запрос, опишите и соберите исправление; клиент проверит оба. Появится ли в наборе «переоткрытие» куска, решится после первого прогона.

**Цепочка: одна большая функция за один прогон**

Бывает, что для клиента это одна вещь, а для сборки — пять кусков: список, страница карточки, два эндпоинта и таблица. По кускам это пять контрактов, пять отправок и пять ожиданий. Цепочка делает это за один прогон и оставляет читателя там, где он нужен.

- **Описание (чат).** Скажите «spec a chain». Контракт — голова цепочки (head): «What users see» для всей функции, проверка клиентом всей функции и Size, где названо всё, что она добавляет, — каждый пункт с полным путём или именем. Вы утверждаете одной строкой, как всегда. В трекер он попадает как Ready с пометкой головы цепочки.
- **Разбиение (вкладка Code).** Выполните `/mg-ship-kit:chain`. Claude берёт голову и разбивает её на подкуски: от двух до шести контрактов, сначала основания, каждый называет только то, что названо в голове, каждый пункт головы попадает ровно в один подкусок, и каждое число равно числу названных пунктов. Любое другое разбиение набор отвергает, как и голову, где названо не всё, что посчитано. Каждый подкусок получает строку в трекере под головой (колонка Head). Затем Claude останавливается и показывает разбиение на одном экране.
- **Go.** Прочитайте подкуски — здесь или в трекере. Скажите «go». Это единственная остановка: после неё Claude собирает подкуски по порядку, каждый через ту же проверку и отправку, что и кусок. Перед каждым следующим подкуском набор сам спрашивает GitHub, зелёная ли проверка на dev (через `gh`, так что один раз `gh auth login`); не зелёная или нет ответа — цепочка останавливается, как бы её ни продолжали.
- **Остановки.** Цепочка останавливает себя только по трём причинам: проверка провалена на том, что требует вашего слова (лишнее, новый пакет); проверка на GitHub красная или недоступна; подконтракт оставляет открытый вопрос (два способа собрать, или нужно то, чего в нём нет, — Claude никогда не правит контракт, чтобы ответить на собственный вопрос). Вы отвечаете или проходите выход через `/mg-ship-kit:cto-check`, затем `/mg-ship-kit:chain` продолжает с места остановки. Что собрано, остаётся где есть.
- **Решение.** Когда последний подкусок попадает на dev, голова переходит в On dev. Клиент проверяет всю функцию по строкам «How to check it» головы и даёт одно решение: `/mg-ship-kit:done` для головы закрывает все подкуски и отвергается, пока какой-то подкусок ещё собирается или удаляется. Неверная часть — новый кусок; голова остаётся на dev. Релиз ждёт всю цепочку, как любой кусок на dev.
- **Цена.** Подкуски восходят к голове, а не к словам клиента, и ошибка в подкуске 1 встраивается во 2–5 до того, как кто-то посмотрит. Остановка на разбиении — где её ловят: читайте подкуски, а не план.
- **Отмена части цепочки.** Цепочка, для которой ничего не собрано, отменяется целиком. Когда подкусок уже собран, цепочка отменяется по подкуску, с последнего; голова следует, когда уйдёт последний. Отмените один подкусок и оставьте остальные — голова стоит на месте: её контракт обещает то, что не будет собрано. Либо одобрите одной строкой правку головы, убирающую эти пункты, либо отмените остальное.
- В трекере, созданном до цепочек, нет колонки Head. Чат сам добавляет её перед своей следующей задачей на странице.

| Команда | Где | Что делает |
| --- | --- | --- |
| «start a project», «file the meeting», «add an idea», «spec a piece», «spec a chain», «status», «give me the project instructions» | чат | скилл ship-spec |
| `/mg-ship-kit:setup` | вкладка Code | один раз на проект; снова, когда меняется трек или плагин не может открыть PR с обновлением |
| `/mg-ship-kit:next` | вкладка Code | взять следующий кусок Ready |
| `/mg-ship-kit:cto-check` | вкладка Code | прогнать проверку, пройти выход, отправить на dev |
| `/mg-ship-kit:chain` | вкладка Code | разбить голову цепочки, остановиться для вашего go, собрать подкуски за один прогон |
| `/mg-ship-kit:done` | вкладка Code | клиент принял |
| `/mg-ship-kit:drop` | вкладка Code | клиент отклонил: удалить код |

## 8. Релиз в main

- Релиз открыт, когда ни один кусок не в Building и не в On dev, то есть у каждого есть решение. Цепочка считается одним куском — её головой. `/mg-ship-kit:done` сообщает, когда он открылся.
- Отправьте dev в main. Шлюз не пускает релиз, пока какой-то кусок собирается или стоит на dev, и выпускает только то, что уже есть на dev.
- Вручную перед каждым релизом, пока это не покрывает набор: у dev и прода разные базы данных; перед каждой миграцией делается бэкап; автоматические ежедневные бэкапы хранятся вне сервера, и последнему меньше суток; восстановление проверено хотя бы раз; откат — одна команда, и он отрепетирован; в репозитории нет секретов; при падении прода приходит оповещение. Заметка о релизе начинается со счёта, например «Floor: 7/7». Ничего не выпускается, пока хоть один пункт провален. Сначала чините его.
- Кто трогает сервер. Ваш собственный сервер: вы и Claude. Облачный сервер клиента: только после тренировок на своём, в plan mode, с одобрением каждой команды. Сервер банка, телекома или госоргана: его настраивает и держит доступ настоящий devops; вы собираете и поддерживаете. Код попадает в прод только через пайплайн, никогда руками по SSH. Claude никогда не работает на проде в auto mode.

## 9. Поддержка

- Сохраните еженедельную встречу с клиентом. Её заметки идут в Meetings; «file the meeting» превращает их в строки Backlog; дальше — шаг 7.
- Баги и запросы лежат в одном Backlog, словами клиента. Один список.

## 10. Чего в наборе ещё нет

Перечислено, чтобы никто этого не ждал:

- Кнопка «проблема» внутри продукта, которая заводит тикеты.
- Проверки сервера и данных в пайплайне. Шаг 8 пока вручную.
- Проверка безопасности кода (нет логина, текст пользователя уходит в SQL, ключи в коде) и проверка библиотек на известные дыры перед релизом.
- Быстрая полоса. Сегодня даже правке в одну строку нужен маленький контракт.
- Проверка продаж при контракте (три человека, которые заплатят, сколько заплатят, кто откроет дверь) и метод исследования.
- Шаг с Claude Design: ссылка на дизайн в контракте.
- Команда проверки настройки. Шаг 6 пока вручную.
- Скилл чата, который обновляется сам. Скиллы чата Claude загружаются вручную, поэтому после изменения набора в `chat/` вы загружаете ship-spec заново. Чат подскажет когда.
- Трек cloudflare. Настройка на нём останавливается, пока не появятся его список стека, подсчёт размера и деплой.

Для глубокого разговора старые роли по-прежнему есть как скиллы в чате: «Summon PM», «Summon CTO», «Summon Client», «Summon Skeptic». Они написаны для Scout и говорят его словами (Build Tracker, Stage 0): берите их для размышлений, а не для шагов Ship.
