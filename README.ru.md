# Ship — руководство

*Это публичная копия руководства. Она публикуется из закрытого репозитория набора при каждом релизе, поэтому правки здесь перезаписываются.*

**v0.1.19 — 12 ноября 2026.** Перевод английской версии v0.1.19 для ship-spec 0.16.1 и плагина mg-ship-kit 0.16.1. Части про деплой (конец шага 5, шаг 8 и главы по трекам) остаются краткими до первых прогонов на каждом треке и будут переписаны по их итогам. Где руководство и набор расходятся, прав набор. Главный текст — английский, [README.md](README.md); при расхождении верен он. Это руководство описывает набор (kit) и никогда не копирует его файлы: точные колонки и команды — по ссылкам.

Вы здесь впервые? Откройте новый чат Claude, вставьте ссылку на эту страницу и попросите провести вас по шагам 1–6.

## Что такое Ship

Создавать, выпускать и поддерживать софт, за который платят, без команды разработчиков.

Вы описываете один небольшой кусок (piece) в чате Claude. Он попадает в трекер проекта в Notion со статусом Ready. Claude Code берёт его, собирает и не может отправить на dev, пока кусок не совпадёт с контрактом, не будет использовать только согласованный стек, не избавится от неиспользуемого кода и не пройдёт проверку безопасности. Клиент проверяет его на dev; его решение закрывает кусок. Релиз в main ждёт, пока у каждого куска на dev есть решение. Куски, которые не зависят друг от друга, собираются одновременно, каждый в своей сессии Claude Code.

Правила, на которых всё держится:

- Вы утверждаете один короткий экран на кусок — контракт. Подробный план Claude нужен Claude, а не вам.
- Собирайте малое на dev и давайте клиенту проверять там. То, чем никто не пользуется, удаляется, а не прячется. Git всё помнит.
- Проваленная проверка останавливает кусок. Сначала чините проверку. Без исключений.
- Каждое решение приходит к вам как одна реальная ситуация, два-три варианта, цена каждого простыми словами и рекомендация. Не поняли — берите рекомендацию.
- Ничто не фиксируется, пока вы не скажете «да» своими словами. Молчание, вопрос или «если не возражаете» не считаются.
- Любая смена курса помечается одной строкой: «CHANGE: …».
- Правила Ship живут в наборе, а не в вашем проекте: чат берёт их из скилла ship-spec, Claude Code — из плагина. Собственные файлы проекта хранят только то, что верно для этого проекта, поэтому изменение набора доходит до каждого проекта без ручного копирования.

## 1. Настройка один раз

На каждого человека и каждую машину. Делается один раз; пункт 8 говорит, что повторять после изменения набора.

1. **Claude.** Установите приложение Claude для компьютера и войдите своим аккаунтом claude.ai с планом, в который входит Claude Code. Вкладка Code — ваша мастерская; она должна быть под тем же аккаунтом (не по API-ключу) и на Claude Code 2.1.273 или новее, потому что плагин приходит в неё из аккаунта. Терминал и VS Code — продвинутые пути; они вам не нужны.
2. **GitHub.** Аккаунт. Репозиторий набора закрытый: попросите владельца добавить вас в организацию mgac-consulting (хватит роли Read). Ваш аккаунт claude.ai читает набор через GitHub-приложение Claude, которому вы даёте доступ к ship-kit в пункте 5.
3. **Notion.** Рабочее пространство, где вы можете добавлять тимспейсы. В аккаунте Claude включите коннектор Notion; вкладка Code пользуется им, когда вы входите с тем же аккаунтом.
4. **На машине.** git и python3; Node.js, если у проектов есть фронтенд. Доступ к GitHub из вкладки Code: `gh auth login`, затем `gh auth setup-git`, или SSH-ключ. Попросите Claude во вкладке Code провести вас по шагам.
5. **Плагин, один раз.** Ship — это один плагин, mg-ship-kit, и вы ставите его один раз на свой аккаунт claude.ai. Он служит обеим сторонам: в чате его скилл ship-spec заводит страницы проектов и специфицирует куски; во вкладке Code его команды, проверки и хуки строят их и охраняют. В claude.ai откройте **Customize → Plugins → Add → Add marketplace**, введите `mgac-consulting/ship-kit`, когда спросят — подключите GitHub и дайте GitHub-приложению Claude доступ к репозиторию, и включите **Sync automatically**. Затем в **Discover** добавьте **Ship kit**. Во вкладке Code ничего не ставьте: она получит плагин из аккаунта при следующем запуске (в открытой сессии выполните `/reload-plugins`). Дальше каждое слияние в main набора доходит до чата и до Code само.
6. **Никаких других копий.** Копия, поставленная во вкладке Code через `/plugin`, важнее копии из аккаунта и не обновляется вместе с ней, а загруженный скилл ship-spec грузится рядом со скиллом плагина. Если у вас есть что-то из этого от прошлого набора, удалите: во вкладке Code `/plugin uninstall mg-ship-kit@ship-kit`, затем `/plugin marketplace remove ship-kit`; в claude.ai в **Customize → Skills** удалите ship-spec. `/mg-ship-kit:setup` предупредит, если копия в Code ещё осталась.
7. **Проверка.** В новом чате вопрос «what version is ship-spec?» называет версию из main набора. Во вкладке Code `/plugin` показывает `mg-ship-kit@synced`, а `/mg-ship-kit:setup` есть в списке команд.
8. **После изменения набора.** README набора говорит, что изменилось. Большая часть теперь приходит сама:
   - **Плагин** — и в чате, и в Code — обновляется сам из аккаунта. В чате он появляется в течение минут после слияния. Code скачивает его при запуске; открытая сессия показывает «Plugins changed. Run /reload-plugins to activate.»
   - **Каждый проект** — на следующей сессии Claude Code в нём: плагин открывает PR в репозитории, который обновляет проверку GitHub, а Claude обновляет строку Kit на странице проекта. Слейте PR в dev, затем подтяните dev. Для PR нужен `gh` с входом; без него Claude скажет выполнить `/mg-ship-kit:setup` и закоммитить `.github/`.
   - **Страница проекта** получает новую колонку или строку от самого чата перед его следующей задачей. Он только добавляет.

   **Один раз, для 0.16.0:** ставить ничего не нужно. Чат сам добавит в трекер колонку Depends on и предложит записать строки Depends on для строк, которые уже Ready; строка без неё собирается по одной, как раньше (шаг 7). **Один раз, для 0.15.0:** в каждом репозитории ещё раз выполните `/mg-ship-kit:setup` на `dev` и закоммитьте то, что он записал (строку Kit и копию CI, в которой теперь лимиты быстрой полосы). После этого `/mg-ship-kit:quick` готова к работе (шаг 7). Теперь Claude может запускать `/mg-ship-kit:cto-check` и `/mg-ship-kit:quick` за вас по вашим словам; набрать команды самому по-прежнему можно. **Один раз, для 0.14.0:** в каждом репозитории ещё раз выполните `/mg-ship-kit:setup` на `dev` и закоммитьте то, что он записал: он делает карту сборки репозитория и её подстраницу «Build map» (шаг 5). Чат сам поднимет страницу до layout 5. **Один раз, для 0.13.0:** ставить ничего не нужно. Если код проекта живёт в нескольких репозиториях, скажите в чате «add a repo» для каждого, из которого вы отправляете куски, выполните `/mg-ship-kit:setup` в каждом из них на `dev` и проставьте Repo у его строк Ready (шаг 3). **Один раз, для 0.7.0:** удалите старые копии (пункт 6) и добавьте плагин в аккаунт (пункт 5). Затем в каждом проекте откройте сессию Claude Code и один раз выполните `/mg-ship-kit:setup`. Он убирает старые строки плагина из `.claude/settings.json`, убирает из `CLAUDE.md` старые строки правил набора (они теперь приходят из плагина) и просит строку Kit. Закоммитьте то, что он изменил. Затем в чате скажите «give me the project instructions» и вставьте их в Claude Project проекта (шаг 4, пункт 5). **Один раз, для 0.4.0:** плагин переименован из `ship` в `mg-ship-kit`, поэтому обновление его не переносит. Выполните `/plugin uninstall ship@ship-kit`, затем `/plugin install mg-ship-kit@ship-kit`, затем `/reload-plugins`. В каждом проекте выполните `/mg-ship-kit:setup` и замените в его `CLAUDE.md` любую команду `/ship:` на `/mg-ship-kit:`; до этого setup будет предупреждать.

## 2. Notion: тимспейс проекта

1. В боковой панели Notion добавьте тимспейс с именем проекта (например «Acme CRM»). Один тимспейс на проект.
2. Участники: вы и ваша команда. Никогда не добавляйте клиента и никогда не делитесь страницей оттуда. Клиент видит продукт на dev и в проде, но не этот тимспейс.
3. Не создавайте в нём страниц вручную. Страница проекта появится на шаге 4.

## 3. GitHub: репозиторий проекта

1. Создайте закрытый репозиторий с именем проекта и README, чтобы в нём был первый коммит. Или во вкладке Code: «создай закрытый репозиторий GitHub с именем … и ветками main и dev и склонируй его сюда».
2. Две ветки. `main` — то, что работает в проде. `dev` — куда попадают куски и где проверяет клиент. Создайте `dev` из `main`.
3. Склонируйте репозиторий на машину и откройте его папку во вкладке Code.
4. Секреты (пароли, ключи, доступы к серверу) живут в env-файле, например `.env`, который git игнорирует. Добавьте `.env` в `.gitignore` до любого коммита, в который он мог бы попасть; первый коммит с одним README — не страшно. Позже настройка добавит все строки для env-файлов, и с того момента push с env-файлом не пройдёт, а каждый push проверяется на ключ, вставленный в код; но файл, закоммиченный раньше, останется в истории git.
5. Существующий проект остаётся в своём репозитории. Пропустите пункт 1, но сделайте пункты 2–4: две ветки, клон, строка про env. Список стека читается из его файлов зависимостей.
6. Несколько репозиториев. Проект, чей код живёт больше чем в одном репозитории (ядро, API, фронтенд — каждый свой репозиторий), настраивается репозиторий за репозиторием: каждый, из которого вы отправляете куски, получает свою настройку (шаг 5) и свою проверку на GitHub, а страница и трекер у проекта одни. В Facts они перечислены под `Repos:`, колонка Repo трекера говорит, в каком репозитории живёт кусок, и Claude Code в одном репозитории видит только его строки. Кусок живёт в одном репозитории; фича, которой нужны два, — это два куска, сначала фундамент. Папка, в которой лежат только другие репозитории (workspace), — не репозиторий Ship: настройка отказывает и называет репозитории, которые надо настроить вместо неё.

## 4. Чат: страница проекта

1. В новом чате Claude скажите «start a project». Отвечает скилл ship-spec.
2. Он перечисляет ваши тимспейсы и спрашивает недостающее: имя проекта, одну строку о том, что он делает, как продаётся (один клиент, несколько клиентов или публичное приложение), каждого клиента с контактом, ссылку на репозиторий (или на каждый репозиторий, когда их несколько; потом «add a repo» добавляет ещё один) и где хранятся секреты. По строке на каждое. Для остального годится «not yet». Затем он ищет в интернете то, что уже существует (D72): продукт, который можно взять, open-source проект для форка, библиотеки для крупных частей. Он показывает вердикт по каждой части — взять (adopt), форкнуть (fork) или строить (build), — каждый с лицензией, и просит одну строку для Facts: `Reuse: adopt | fork | build — что, лицензия`. Строку он пишет только после вашего «да». Скажите «skip», чтобы пропустить поиск. Ещё он предлагает исследование рынка (D85): как другие уже решили эту задачу для пользователей — не больше пяти находок со ссылками и чего не хватает везде. После вашего «да» оно запускается и предлагает ещё одну строку для Facts: `Market: ближайший конкурент — что делает, чего не хватает`.
3. Он выбирает трек (track): где проект работает и на каком стеке. Он задаёт до четырёх простых вопросов (есть ли клиент — банк, телеком или госорган? есть ли в команде devops? в основном работа с данными или страницы и формы? можете ли платить картой от $5 в месяц?) и называет трек с причиной: devops, railway или cloudflare. Вас никогда не спрашивают «какой стек?». Если хотите другой трек и можете сказать почему, скажите: ваш трек и ваша причина попадут в строку Track. Если клиент — банк, телеком или госорган, а devops нет, всё останавливается здесь: сначала найдите devops.
4. Он строит страницу в корне тимспейса, читает её обратно и проверяет, что все части на месте. Вы получаете ссылку.
5. Он даёт короткий блок инструкций для Claude Project этого проекта. Создайте Claude Project с именем проекта и вставьте блок в его инструкции, один раз. Менять его не нужно: он велит чату загружать ship-spec и хранит только стиль ответов (один экран, одно решение, ничего не фиксируется без вашего «да»). Всё остальное приходит из скилла, который обновляется вместе с набором. Потеряли — скажите «give me the project instructions».
6. Последней строкой он отправляет вас к `/mg-ship-kit:setup`. Пока ничего не описывайте: сначала настройте репозиторий (шаг 5) и пройдите чек-лист (шаг 6).

Страница сверху вниз. Точные строки, колонки и представления лежат в [plugins/mg-ship-kit/skills/ship-spec/page-layout.md](https://github.com/mgac-consulting/ship-kit/blob/main/plugins/mg-ship-kit/skills/ship-spec/page-layout.md); руководство их не копирует.

| Часть | Что в ней | Кто пишет |
| --- | --- | --- |
| Facts (факты) | Постоянные факты и ссылки: что делает, как продаётся, трек, клиенты и контакты, репозиторий (или список репозиториев), ссылки на dev и прод, папка на Drive, дизайн-система, где хранятся секреты. Сами секреты — никогда. | Чат при старте; вы поправляете |
| Tracker (трекер) | Одна строка на кусок: имя, порядок, статус (Ready → Building → On dev → Done, или Dropped), размер, файл контракта, безопасность (итог проверки), репозиторий (в каком он живёт), зависимости (Depends on: куски, которые должны быть на dev раньше). Полный контракт лежит внутри строки. | Чат добавляет строки Ready; после взятия в работу — только Claude Code |
| Meetings (встречи) | Одна строка на встречу с клиентом, заметки в теле. Отмечается галочкой, когда каждый запрос разнесён. | Вы; галочку ставит чат |
| Backlog (бэклог) | Одна строка на запрос: кто сказал (клиент, ваши заметки о клиенте, пользователь, ваша идея, конкурент), точные слова, какой клиент просил, статус (New → Specced, или Dropped), ссылка на кусок и его живой статус. | Чат, из того, что вы ему даёте: заметки встречи, идея, скриншот, слова пользователя. Строку можно добавить и руками |
| Notes (заметки) | Ваши. Ни один инструмент их не читает. | Вы |
| Build map — *репозиторий* (карта сборки) | Одна подстраница на каждый настроенный репозиторий (D91): как устроен проект, чтобы чат описывал куски под то, что уже есть. Таблицы с ключевыми колонками, эндпоинты и экраны, посчитанные из кода тем же кодом, что и проверка размера, плюс несколько строк о ключевых решениях и известных пробелах. Она называет коммит dev, который описывает, и говорит, менялся ли dev с тех пор. Копия `contracts/map/build-map.md` только для чтения. | Только Claude Code: setup создаёт её, каждый `/mg-ship-kit:done` переписывает; правка вручную его останавливает |

Правила для всей страницы: нигде ни пароля, ни ключа, ни доступа к серверу. Представления сортируют и никогда не фильтруют. Строки помечаются Dropped, а не удаляются.

## 5. Code: настройка репозитория

1. На своём компьютере, во вкладке Code, в папке репозитория, на ветке `dev`, выполните `/mg-ship-kit:setup`. Первую настройку нельзя сделать в облачной сессии: плагина там ещё нет. Сначала он просит ссылку на страницу проекта. Вставьте её. Он читает трек из Facts. На треке cloudflare он останавливается здесь и ничего не пишет: этот трек ещё не построен. Он так же останавливается и ничего не пишет, когда у репозитория нет `origin`, когда `dev` ещё нет на GitHub, когда вы на другой ветке или когда найденный код принадлежит другому репозиторию (репозиторий внутри этого, или папка, которую закрывает `.gitignore`): он называет репозиторий, который надо настроить вместо этого. Он никогда не спрашивает вас, куда положить проверку; ответ всегда один — «в репозиторий, чей это код».
2. Он находит папки бэкенда и фронтенда и пишет `ship.json` со списком стека, прочитанным из файлов зависимостей. В пустом репозитории он берёт стек набора по умолчанию (FastAPI, Postgres, React, в `backend/` и `frontend/`) — это стек треков devops и railway. Если в строке Track назван другой стек, скажите сейчас; тогда он начнёт с пустого списка и нужных папок.
3. Он читает список стека обратно: «n Python packages, n Node packages». С этого момента всё новое останавливает кусок, пока вы не одобрите одной строкой.
4. Он создаёт `contracts/` и `CLAUDE.md` из шаблона набора. Заполните заготовки вместе с Claude по тому, что видно в коде. `CLAUDE.md` хранит только то, что верно для этого проекта: что это, его стек, его команды, его собственные правила. До 150 строк, без кода. Правил Ship в нём нет: плагин добавляет их в каждую сессию, поэтому они обновляются вместе с плагином. В уже существующем `CLAUDE.md` настройка убирает строки, копирующие старые правила набора, и добавляет одну строку о том, откуда берутся правила. Строка набора, которую вы правили вручную, остаётся; Claude показывает её и спрашивает: удалить или оставить как правило проекта.
5. Он привязывает трекер на странице, которую вы вставили, и говорит «linked the tracker», и записывает имя репозитория в `ship.json` (из его ссылки на GitHub): в проекте с несколькими репозиториями здесь берутся в работу только строки трекера, у которых колонка Repo называет это имя. Затем пишет строку Kit в Facts (`Kit: mg-ship-kit` и версия). Чат проверяет эту строку перед каждой задачей, так что отставшая копия — в чате или в Code — видна сразу. Последним он пишет карту сборки репозитория: числа из кода на dev и до десяти строк о решениях и пробелах, которые Claude читает из кода. Карта лежит в `contracts/map/`, а её копия только для чтения — подстраница «Build map» на странице проекта.
6. Он называет каждый инструмент проверки — `vulture` для бэкенда и `knip` для фронтенда — как найденный, как MISSING со строкой установки или как «needed once backend/ exists» в пустом репозитории. MISSING ставьте сейчас; «needed once» — как только первый кусок создаст эту папку, до `/mg-ship-kit:cto-check`. Без них проверка не проходит. Он также ищет `gitleaks` — сканер секретов, который нужен каждому push (D67): поставьте его один раз на каждую машину, где собираете (`brew install gitleaks` на Mac или файл со страницы релизов gitleaks; версию печатает настройка). Без него не пройдёт ни один push. Когда gitleaks появится, настройка один раз просканирует всю историю репозитория и перечислит найденные ключи. Этот список ничего не блокирует: ключ, который хоть раз был запушен, раскрыт, поэтому замените его там, где он выдан. Если он предупреждает, что git отслеживает env-файл, уберите файл из git, как он говорит, и смените любой пароль, который там был.
7. Он записывает проверку GitHub в `.github/`. С этого момента GitHub прогоняет ту же проверку при каждом push в dev и main (а в остальных ветках — короткое сканирование секретов), и ничего не деплоится, пока она не пройдёт. Не правьте эти файлы. После обновления плагина он сам открывает PR, который их обновляет, на следующей сессии; слейте его. Ещё он добавляет env-файлы в `.gitignore`, и с этого момента любой push с таким файлом не пройдёт.
8. Плагин приходит из вашего аккаунта claude.ai, поэтому репозиторий ничего не объявляет. Если `.claude/settings.json` называет набор после прошлой настройки, она убирает эти строки (или удаляет файл, если в нём больше ничего нет): копия, объявленная в репозитории, была бы важнее копии из аккаунта и обновлялась бы сама по себе. Если на этой машине ещё есть копия, поставленная через `/plugin`, настройка предупредит и покажет, как её удалить.
9. Закоммитьте добавленные и изменённые файлы и отправьте их в dev. В этом push нет кода продукта, поэтому шлюз его пропускает. Затем откройте на GitHub вкладку Actions репозитория: через несколько минут проверка Ship check для этого push становится зелёной. Красная или её нет: остановитесь и почините. Каждый деплой ждёт её. Тесты набора подменяют GitHub, так что первый push вашего проекта — настоящая проверка workflow; если она красная, сначала прочитайте лог запуска.
10. Подключите деплой. Настройка заканчивается одной строкой для вашего трека; подробности — в `.github/ship/README.md` в вашем репозитории. Трек devops: отдайте этот файл своему devops (раздел «Your devops»); его деплой запускается только после того, как прошла Ship check. Трек railway: следуйте разделу «Railway» и попросите Claude провести вас по шагам.
11. Когда ссылка на dev открывается, запишите её в строку Dev URL в Facts. Ждать её не нужно: описывайте и собирайте, пока деплой настраивается. Кусок, который попал на dev раньше, ждёт там ссылку и решение клиента. Live URL появится с первым релизом (шаг 8).

## 7. Сборка куска

**Сбор запросов (чат)**

- После встречи с клиентом добавьте строку в Meetings с заметками в теле: набранными, вставленными или текстом записи. Затем скажите «file the meeting». Чат перечисляет каждый запрос, слова скопированы точно; вы говорите «да»; каждый становится строкой Backlog.
- Ваша идея или экран конкурента: «add an idea», со скриншотом. Отзыв, тикет или сообщение пользователя: вставьте его; оно разносится как слова пользователя и никогда не переформулируется.
- Ничего не выдумывается. Запрос, которого нет в Backlog, сначала добавляется.

**Сначала обдумать (чат, по желанию)**

До описания помогают три роли. Каждая — это способ разговора, а не шаг: ни одна не пишет контракт и строку трекера.
- **«Summon PO»**: называет проблему за запросом, давит на слабые места и предлагает два-три способа нарезать работу — со своим выбором. В конце называет срез и его строки Backlog; скажите «spec it», и чат набросает контракт.
- **«Summon Client»**: играет собственного клиента проекта — по Facts, заметкам встреч и запросам этого клиента, от первого лица: боль и возражения, никогда не решения. Его слова никогда не доказывают, что кто-то заплатит, а всё, что стоит сохранить, заводится как ваша идея, а не слова клиента.
- **«Summon Architect»**: устройство системы — новый проект, как резать цепочку, модель данных. Работает в чате и во вкладке Code, где ещё читает репозиторий. Никогда не правит код и список стека. Это не CTO-проверка.
- **Исследование рынка** (D85): когда PO считает запрос новым для команды, он одной строкой предлагает исследование рынка и ждёт его, прежде чем нарезать. Находки пишутся в строку запроса в Backlog, с датой. Старше шести месяцев — помечаются, и предлагается новый прогон. Во вкладке Code оно идёт в фоне.

**Описание (чат)**

- Скажите «spec a piece». Чат показывает запросы New; вы выбираете один или несколько. Он набрасывает контракт на один экран: слова, из которых он вырос; что видят пользователи; чего нет; как проверить («When I …, then I see …»); размер в числах — экраны, эндпоинты, таблицы. Перед черновиком он читает карту сборки репозитория куска, поэтому черновик называет уже существующую таблицу или маршрут, а не угадывает; он называет то, на что опирается, чтобы ошибка была видна. Устаревшая карта (dev с тех пор менялся) всё равно читается, с предупреждением. Перед головой цепочки он просит вас попросить Claude Code подтвердить два-три утверждения карты, на которые опирается цепочка: возраст карты виден, неверная строка — нет.
- Прочитайте. Утвердите одной строкой или скажите, что поменять. В проекте с несколькими репозиториями чат говорит, в каком репозитории живёт кусок, и почему; вы можете назвать другой. Колонка Repo строки несёт это имя, и кусок берёт в работу только Claude Code в этом репозитории. После утверждения кусок получает строку Tracker со статусом Ready, а его запросы становятся Specced и ссылаются на него.
- Каждый черновик говорит, от чего кусок зависит (D93): какие куски должны быть на dev, прежде чем его можно собирать, или ни от каких. Кусок зависит от другого, когда использует или меняет таблицу, эндпоинт или экран, которые тот добавляет или меняет, а тот ещё не Done. Два куска, которые добавляют или меняют таблицы, зависят всегда: их миграции базы должны идти по порядку. Кусок без зависимостей может собираться рядом с другими. Когда чат не уверен, он называет зависимость: пропущенная обойдётся остановкой позже, названная только подождёт.
- Если одна проверка клиентом его не покрывает, разделите на куски — или опишите как цепочку (ниже), чтобы Claude Code собрал части за один прогон.

**Взятие в работу и сборка (вкладка Code)**

- Выполните `/mg-ship-kit:next`. Он берёт кусок Ready с наименьшим Order из строк этого репозитория, у которого все зависимости в On dev или Done, сохраняет контракт в `contracts/`, ставит строке Building и записывает в неё копию только для чтения. Эту копию пишет только Claude Code; правка вручную его останавливает.
- Чтобы собирать два куска сразу (D93), откройте вторую сессию со своей копией репозитория — новую облачную или сессию в десктоп-приложении в своём worktree — и выполните `/mg-ship-kit:next` там. В одной сессии собирается один кусок; две сессии в одной папке не могут собирать обе: второй `/mg-ship-kit:next` видит первый кусок и отказывает. Запускайте их по очереди: дождитесь, пока первая покажет свою строку как Building. Каждая лишняя сессия — это ещё одна проверка, ревью и проверка клиентом для вас; параллель окупается, только когда вы ждёте Claude дольше, чем Claude ждёт вас.
- Строка, описанная до Depends on, собирается, только пока ничего больше из её репозитория не собирается, как раньше; скажите в чате «add the Depends on lines», чтобы это изменить.
- Claude собирает то, что перечислено в контракте, и ничего больше. Вы читаете один экран, а не план.
- Изменение, которое клиент просит по ходу сборки, — это изменение контракта: вы одобряете его одной строкой. Claude никогда не правит контракт сам.

**Проверка (вкладка Code)**

- Выполните `/mg-ship-kit:cto-check`. Три проверки: Size (что собрано против списка), Stack (пакет или импорт вне списка), Leftovers (неиспользуемый код в добавленных строках, его находят vulture и knip). Проваленная проверка останавливает кусок.
- Выход. Лишнее, о чём просил клиент: вы одобряете изменение контракта одной строкой. Лишнее, о чём никто не просил: Claude удаляет. Новый пакет: вы одобряете одной строкой, или Claude убирает его. Leftovers: Claude удаляет. Затем проверка идёт снова.
- При прохождении та же команда запускает проверку безопасности (D66). Скрипт, а не Claude, решает, задевает ли кусок рискованное: маршруты, базу данных, логин и права, загрузку файлов, конфиг и env, новый пакет. Кусок, который не задевает, получает пометку о пропуске. Тот, что задевает, читает агент-ревьюер: он видит diff, контракт и репозиторий, но никогда не видит план Claude и чат. Затем агент-проверяющий пытается доказать каждую находку тестом. Считается только доказанная находка.
- Доказанная critical или major находка останавливает кусок. Выход: Claude исправляет, пока её тест не пройдёт (тест остаётся в репозитории), или вы снимаете её одной строкой со своей причиной. Claude никогда не снимает находку сам. Итог лежит в `contracts/reviews/` и в колонке Security строки трекера, например «2 found, 1 fixed, 1 waived».
- Проверка стоит токенов: два агента на каждый рискованный кусок. `spend` в `ship.json` выбирает модели: `lean`, `standard` (по умолчанию) или `deep`. Для банка или телекома берите deep, для побочного проекта — lean. `review_all: true` проверяет каждый кусок; `review_paths` добавляет путь, который скрипт пропустил.
- При прохождении Claude может предложить строку-две для `CLAUDE.md` из того, чему научил кусок. Одобрите одной строкой или откажите.

**На dev (вкладка Code)**

- Каждый push в любую ветку сначала проверяется на секреты (D67–D70): gitleaks читает каждый коммит, которого ещё нет на GitHub, поэтому ключ, добавленный и потом удалённый, всё равно найдётся. Находка останавливает push до того, как ключ покинет вашу машину. Выход: Claude убирает ключ из кода и из этих коммитов, а вы заменяете его, если он хоть раз куда-то пушился. Ложную тревогу (тестовое значение, пример ключа) снимаете только вы, одной строкой; Claude записывает её в `.gitleaksignore` с вашими словами. Комментарий `gitleaks:allow` в коде ничего не снимает. GitHub ещё раз сканирует каждую ветку, поэтому push из вашего собственного терминала тоже ловится, хотя к тому моменту ключ уже на GitHub.
- Если пока этот кусок собирался, другая сессия отправила свой кусок на dev, `/mg-ship-kit:cto-check` сначала подтягивает этот кусок к dev (делает rebase). Он останавливается и спрашивает вас, когда оба куска меняли один и тот же файл или их изменения конфликтуют: значит, они всё-таки не были независимыми. Решаете вы: свести их вместе здесь или удалить этот кусок и описать его заново с зависимостью от другого. Два куска, каждый из которых добавил миграцию базы, не проходят проверку, пока одна из миграций не будет указывать на другую.
- Скажите «push». Шлюз (gate) прогоняет проверку ещё раз, не пропускает незакоммиченные изменения и не пропускает кусок, у которого нет проверки безопасности, она относится к старому коду или в ней открыта доказанная critical или major находка; GitHub прогоняет ту же проверку ещё раз, прежде чем что-либо деплоится. Строка переходит в On dev.
- Попросите клиента проверить кусок на Dev URL по строкам «How to check it».
- Сразу начинайте следующий кусок через `/mg-ship-kit:next`. Куски на dev не блокируют следующий.

**Решение клиента (вкладка Code)**

- Принято: `/mg-ship-kit:done`. Строка становится Done, а карта сборки перестраивается по dev: числа — скриптом, строки о решениях и пробелах — Claude (не больше десяти), затем её копия на странице.
- Отклонено: `/mg-ship-kit:drop`. Код удаляется, строка становится Dropped. Git всё помнит. Пока от куска зависит другой открытый кусок, удаление отклоняется и называет этот кусок: сначала удалите его или измените в чате.
- Почти верно: пока — оставьте на dev, занесите правку как новый запрос, опишите и соберите исправление; клиент проверит оба. Появится ли в наборе «переоткрытие» куска, решится после первого прогона.

**Быстрая правка: одно слово, одна надпись (вкладка Code)**

- Для правки, которую решаете вы сами: слово, надпись, цвет, отступ. Скажите её во вкладке Code своими словами или наберите `/mg-ship-kit:quick change "Sign in" to "Log in" on /login`. Описания в чате нет (D92).
- Claude пишет крошечный контракт из ваших слов (Size 0, ваше имя и дата как одобрение), добавляет в трекер строку `Quick: …`, делает правку и прогоняет проверку CTO. По вашему «да» отправляет на dev.
- Скрипт держит правку в рамках полосы, а шлюз и GitHub проверяют ещё раз: не больше 10 добавленных и 10 удалённых строк, не больше 3 уже существующих файлов; ни нового, ни удалённого, ни двоичного файла; ни файла зависимостей, деплоя, env, SQL или миграции. Ничто в `ship.json` не поднимает эти лимиты. Если правка выходит за них, Claude урезает её до вашей строки или говорит, что для быстрой полосы она велика, и вы описываете её в чате.
- Проверка безопасности всё равно идёт, если скрипт отметил файл, например страницу входа.
- Пока собирается другой кусок или открыта цепочка, правка ждёт, и Claude возвращает вам вашу строку, чтобы запустить её позже. Ведите список и запускайте их, когда кусок уже на dev.
- Не для багов. Баг, о котором сообщил клиент, — это кусок с `Fixes:`, чтобы его урок не пропал (шаг 9). Неверная цена — баг, даже если это одно слово.
- Решение даёте вы, а не клиент: проверьте на Dev URL, затем `/mg-ship-kit:done`, или `/mg-ship-kit:drop`, если неверно. До тех пор правка блокирует релиз, как любой кусок на dev.
- Claude запускает её только по вашим словам, никогда по своей идее. Опечатку, которую он заметил, он называет вам и ждёт.

**Цепочка: одна большая функция за один прогон**

Бывает, что для клиента это одна вещь, а для сборки — пять кусков: список, страница карточки, два эндпоинта и таблица. По кускам это пять контрактов, пять отправок и пять ожиданий. Цепочка делает это за один прогон и оставляет читателя там, где он нужен.

- **Описание (чат).** Скажите «spec a chain». Контракт — голова цепочки (head): «What users see» для всей функции, проверка клиентом всей функции и Size, где названо всё, что она добавляет, — каждый пункт с полным путём или именем. Перед черновиком чат предлагает исследование рынка (если в запросах ещё нет свежих находок), затем ищет библиотеки, которые уже делают части функции (D72), начиная со строки Reuse в Facts. В голове есть блок Reuse: по строке на часть — взять (adopt) названный пакет с его лицензией или строить (build) и почему. Утверждая голову, вы утверждаете эти пакеты, и сборка не остановится на них (D73). Лицензия не из разрешительных (LGPL, GPL, AGPL, без лицензии) требует ваших слов в её строке, «ok: и почему», иначе Claude Code откажет голове (D74): AGPL-библиотека в веб-приложении клиента может обязать вас опубликовать его исходный код. Вы утверждаете одной строкой, как всегда. В трекер он попадает как Ready с пометкой головы цепочки.
- **Разбиение (вкладка Code).** Выполните `/mg-ship-kit:chain`. Claude берёт голову и разбивает её на подкуски: от двух до шести контрактов, сначала основания, каждый называет только то, что названо в голове, каждый пункт головы попадает ровно в один подкусок, и каждое число равно числу названных пунктов. Любое другое разбиение набор отвергает, как и голову, где названо не всё, что посчитано. Каждый подкусок получает строку в трекере под головой (колонка Head). Затем Claude останавливается и показывает разбиение на одном экране.
- **Go.** Прочитайте подкуски — здесь или в трекере. Скажите «go». Это единственная остановка: после неё Claude собирает подкуски по порядку, каждый через ту же проверку и отправку, что и кусок. Перед каждым следующим подкуском набор сам спрашивает GitHub, зелёная ли проверка на dev (через `gh`, так что один раз `gh auth login`); не зелёная или нет ответа — цепочка останавливается, как бы её ни продолжали.
- **Остановки.** Цепочка останавливает себя только по трём причинам: проверка провалена на том, что требует вашего слова (лишнее, новый пакет); проверка на GitHub красная или недоступна; подконтракт оставляет открытый вопрос (два способа собрать, или нужно то, чего в нём нет, — Claude никогда не правит контракт, чтобы ответить на собственный вопрос). Вы отвечаете или проходите выход через `/mg-ship-kit:cto-check`, затем `/mg-ship-kit:chain` продолжает с места остановки. Что собрано, остаётся где есть.
- **Решение.** Когда последний подкусок попадает на dev, голова переходит в On dev. Клиент проверяет всю функцию по строкам «How to check it» головы и даёт одно решение: `/mg-ship-kit:done` для головы закрывает все подкуски и отвергается, пока какой-то подкусок ещё собирается или удаляется. Неверная часть — новый кусок; голова остаётся на dev. Релиз ждёт всю цепочку, как любой кусок на dev.
- **Цена.** Подкуски восходят к голове, а не к словам клиента, и ошибка в подкуске 1 встраивается во 2–5 до того, как кто-то посмотрит. Остановка на разбиении — где её ловят: читайте подкуски, а не план.
- **Отмена части цепочки.** Цепочка, для которой ничего не собрано, отменяется целиком. Когда подкусок уже собран, цепочка отменяется по подкуску, с последнего; голова следует, когда уйдёт последний. Отмените один подкусок и оставьте остальные — голова стоит на месте: её контракт обещает то, что не будет собрано. Либо одобрите одной строкой правку головы, убирающую эти пункты, либо отмените остальное.
- В трекере, созданном до цепочек, нет колонки Head. Чат сам добавляет её перед своей следующей задачей на странице. То же с колонкой Repo (набор 0.13); цепочка строится в одном репозитории, и её подкуски наследуют репозиторий головы.

| Команда | Где | Что делает |
| --- | --- | --- |
| «start a project», «file the meeting», «add an idea», «spec a piece», «spec a chain», «status», «give me the project instructions» | чат | скилл ship-spec |
| `/mg-ship-kit:setup` | вкладка Code | один раз на репозиторий, на dev; снова, когда меняется трек или плагин не может открыть PR с обновлением |
| `/mg-ship-kit:next` | вкладка Code | взять следующий кусок Ready, чьи зависимости уже на dev; во второй сессии — второй кусок рядом с первым |
| `/mg-ship-kit:cto-check` | вкладка Code | прогнать проверку и проверку безопасности, пройти выход, отправить на dev |
| `/mg-ship-kit:quick` | вкладка Code | правка в одну строку вашими словами, без описания; вы проверяете её на dev |
| `/mg-ship-kit:chain` | вкладка Code | разбить голову цепочки, остановиться для вашего go, собрать подкуски за один прогон |
| `/mg-ship-kit:done` | вкладка Code | клиент принял; перестраивает карту сборки |
| `/mg-ship-kit:drop` | вкладка Code | клиент отклонил: удалить код |

## 8. Релиз в main

- Релиз открыт, когда на dev нет куска без решения клиента и ничего недособранного. Цепочка считается одним куском — её головой. Кусок, который собирается в другой сессии, ещё не на dev, поэтому он не уходит в релиз и не держит его. `/mg-ship-kit:done` сообщает, когда релиз открылся, и называет то, что ещё собирается в других сессиях.
- Отправьте dev в main. Шлюз не пускает релиз, пока какой-то кусок собирается или стоит на dev, и выпускает только то, что уже есть на dev.
- Вручную перед каждым релизом, пока это не покрывает набор: у dev и прода разные базы данных; перед каждой миграцией делается бэкап; автоматические ежедневные бэкапы хранятся вне сервера, и последнему меньше суток; восстановление проверено хотя бы раз; откат — одна команда, и он отрепетирован; в репозитории нет секретов (сканирование покрывает каждый коммит после настройки; вручную проверьте, что со списком из истории разобрались); при падении прода приходит оповещение. Заметка о релизе начинается со счёта, например «Floor: 7/7», затем строка о снятых находках, которую печатает `/mg-ship-kit:done`, когда релиз открыт: «Waived: 0» или каждая снятая находка. Ничего не выпускается, пока хоть один пункт провален. Сначала чините его.
- Кто трогает сервер. Ваш собственный сервер: вы и Claude. Облачный сервер клиента: только после тренировок на своём, в plan mode, с одобрением каждой команды. Сервер банка, телекома или госоргана: его настраивает и держит доступ настоящий devops; вы собираете и поддерживаете. Код попадает в прод только через пайплайн, никогда руками по SSH. Claude никогда не работает на проде в auto mode.

## 9. Поддержка

- Сохраните еженедельную встречу с клиентом. Её заметки идут в Meetings; «file the meeting» превращает их в строки Backlog; дальше — шаг 7.
- Баги и запросы лежат в одном Backlog, словами клиента. Один список.
- Баг становится задачей с пометкой `Fixes:` (D77): чат добавляет эту строку, когда запрос говорит, что что-то сломалось, и вы можете поправить это при утверждении. Исправление бага не проходит проверку, пока Claude не запишет, что остановит его в следующий раз (D76, D78): тест, который падает на этом баге, строку для CLAUDE.md проекта (только с вашего «да») или, если ошибку должен был поймать сам kit, issue в ship-kit с меткой `lesson` (D79). Списка правил, которые надо помнить, нет: каждый урок — это то, что запускается, или факт, который читает Claude. Время от времени разбирайте issue с меткой `lesson` в ship-kit: хорошие становятся проверками kit.

## 10. Чего в наборе ещё нет

Перечислено, чтобы никто этого не ждал:

- Кнопка «проблема» внутри продукта, которая заводит тикеты.
- Проверки сервера и данных в пайплайне. Шаг 8 пока вручную.
- Проверка библиотек на известные дыры перед релизом (в пакетах, которые уже стоят). Проверка безопасности смотрит на то, что добавляет каждый кусок.
- Проверка продаж при контракте (три человека, которые заплатят, сколько заплатят, кто откроет дверь) и исследование покупателей. Поиск готовых решений и исследование рынка уже есть (шаг 4, шаг 7 и цепочки).
- Шаг с Claude Design: ссылка на дизайн в контракте.
- Команда проверки настройки. Шаг 6 пока вручную.
- Трек cloudflare. Настройка на нём останавливается, пока не появятся его список стека, подсчёт размера и деплой.
- Облачные сессии с плагином. Claude Code в вебе может не загружать плагины из аккаунта и никогда не добавляет маркетплейс самого репозитория. Пока облачная сессия не проверена, стройте куски Ship во вкладке Code приложения.

Старые роли Scout (PM, CTO, Client, Skeptic) выведены из оборота (D84): PO, Client и Architect идут с плагином (шаг 7). Если они ещё загружены в ваш аккаунт, удалите их в Customize → Skills, иначе на «Summon Client» может ответить старый Client.
